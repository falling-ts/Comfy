# MiniMax H3 2752×1536 参考图：max / match 的成本收益与 max 下的最优参考分辨率（源码级复算）

> 日期：2026-10-02
> 对象：ComfyUI 核心 H3 节点（本机 v0.37.0）`MiniMaxH3ReferenceToVideo.ref_image_size`
> 问题：把一张 **2752×1536** 的参考图喂给 H3，`match` 与 `max` 分别带来什么质量与速度差异；如果确定用 `max`，应该准备哪个分辨率的参考图最划算
> 依据：口径与公式直接读源码（`comfy_extras/nodes_minimax_h3.py` L296-311 等），数字按源码公式复算（复跑脚本见 §9）
> 相关：`docs/MiniMax-H3-参考图尺寸与match-max口径-2026-10-02.md`（match/max 全口径与 token 口径）、`docs/MiniMax-H3-参考保真度调研-2026-09-18.md`（保真度杠杆）、`docs/MiniMax-H3-场景参考方式调研-2026-08-17.md`（多图 / 参考板）
> 前置结论（来自口径文档）：`match` = 面积对齐生成画布（只缩不放）；`max` = 短边压到 **2048**（只缩不放）；同一份 resized 同时喂 Qwen3-VL 与 VAE；每 32×32 像素 = 1 个 token

## 0. 结论摘要

1. **2752×1536 的短边 1536 < 2048，所以 `max` 对它根本不缩放**——原样进入模型。`max` 不是"归一化到 2048"，而是"**封顶**在 2048"。
2. 因此 `max` 下的参考密度是 **4128 token**（86×48），只有 2048 封顶值（16:9 → 7296）的 **57%**；2752/32 = 86、1536/32 = 48 都是整数 ⇒ **零对齐损失、零重采样**。
3. **速度**（5 s，视频 token：480p = 14430 / 768p = 37296；文本+音频粗估 800）：
   | 生成档 | `match` | `max` | 序列增幅 | 注意力 FLOPs |
   |---|---|---|---|---|
   | 480p（832×480） | 832×480 / 390 token | 2752×1536 / 4128 token | **+23.9%** | **≈1.54×** |
   | 768p（1344×768） | 1344×768 / 1008 token | 2752×1536 / 4128 token | **+8.0%** | **≈1.17×** |
   作为对比：同样一张图若给 4K（3840×2160），`max` 会压到 3648×2048 / 7296 token，480p 注意力 **2.08×**、768p **1.35×**。**用 2752×1536 而不是 4K，480p 省掉约 26% 的注意力开销，768p 省约 13%。**
4. **真正的大头是 Qwen3-VL-32B 的一次性 prefill**：vision token 从 390（480p match）/ 1008（768p match）涨到 **4128**（×10.6 / ×4.1），vision encoder 要过 16512 个 patch（4K 档是 29184）。本机 8 GB 卡跑 27 GB 的 int8 编码器，大量层在 CPU/内存侧 ⇒ **"max 明显变慢"主要慢在这段，而不是采样步数**。
5. **`max` 下"用哪个分辨率"的答案：素材分辨率本身就是密度旋钮，上限是短边 2048。** 超过 2048 会被压回（传 4K / 8K 与传 3648×2048 完全等价），低于 2048 则原样保留、按比例损失密度。16:9 的甜点是 **3648×2048（7296 token，封顶）**；2752×1536 是它的 **57%**。
6. **`match` 与 `max` 在"素材面积 ≤ 生成画布面积"时完全等价**（480p ≤ 0.40 MP、768p ≤ 1.03 MP）——小图不必纠结这个开关。
7. **2752×1536 恰好是 Qwen-Image 2.1 的原生 16:9 输出档**，而 H3 的 `max` 对它不缩 ⇒ 从 Qwen 到 H3 **零重采样**，是整条链路最干净的一条。**把它放大到 3648×2048 再喂 H3 是净亏**：token 从 4128 涨到 7296（+77%），但插值不产生新信息，身份/文字保真不会提升，还多付 35% 注意力成本。
8. **质量/速度最优解**：768p 生成 → 无条件 `max`（素材尽量给到短边 2048）；480p 生成 → 默认 `match`，只把"人脸 / 文字 / logo 是主体"的 1–2 张切 `max`，且素材保持 **2752×1536**（1.54× 是 480p 的性价比点，再往上到 3648×2048 要付 2.08×）。
9. ⚠️ 本文全部数字来自**源码公式复算，没有跑过生成 A/B**；墙钟倍数与保真提升幅度待实测（§8）。

## 1. 2752×1536 在两档下的实际口径

`ComfyUI/comfy_extras/nodes_minimax_h3.py` L296-311（有效逻辑 6 行）：

```python
if ref_image_size == "match":
    scale = min(1.0, math.sqrt((width * height) / (w * h)))   # 面积对齐生成画布，只缩不放
else:
    scale = min(1.0, REF_IMAGE_SHORT_EDGE / min(w, h))       # 短边 2048，只缩不放
tw = max(CANVAS_MULTIPLE, round(w * scale / CANVAS_MULTIPLE) * CANVAS_MULTIPLE)
th = max(CANVAS_MULTIPLE, round(h * scale / CANVAS_MULTIPLE) * CANVAS_MULTIPLE)
```

- `match` @480p：`scale = √(832×480 / 2752×1536) = √0.09448 = 0.3074` ⇒ 846×472 ⇒ 32 对齐 **832×480**，token = 26×15 = **390**。
- `match` @768p：`scale = √(1344×768 / 2752×1536) = √0.24418 = 0.4942` ⇒ 1360×760 ⇒ 32 对齐 **1344×768**，token = 42×24 = **1008**。
- `max`：`scale = min(1, 2048/1536) = min(1, 1.333) = 1.0` ⇒ **2752×1536 原样**，token = 86×48 = **4128**。

**关键机制：`max` 是封顶而非归一化。** 因为 `scale` 之上还压着 `min(1.0, …)`，短边小于 2048 的素材**不会被放大**，短边大于 2048 的素材才会被压回 2048。所以：

- 2752×1536 在 `max` 下 = "原样直通"，`max` 相对 `match` 的全部收益都来自**原图本身比画布大 10.6×**；
- 期望更多细节时，**必须提高素材本身的分辨率**，切换 `max` 开关本身不会再给更多。

## 2. 速度：成本构成与倍数

参考图 latent 在 pack 里 `img_update=False`——**从不加噪、每一步采样都参与 full attention**，所以采样阶段随序列长度呈 O(S²)。

口径：视频 token = `(W/32)×(H/32) × latent_t`，5 s ≈ latent_t 37 ⇒ 480p 14430 / 768p 37296；文本 + 音频粗估 800。

| 生成档 | 视频 token | 序列（match） | 序列（max） | 序列增幅 | 注意力 FLOPs |
|---|---|---|---|---|---|
| 480p | 14430 | 15620 | 19358 | +23.9% | **1.54×** |
| 768p | 37296 | 39104 | 42224 | +8.0% | **1.17×** |

两段成本中，**采样只是一半**：

1. **采样阶段**：上表的注意力倍数（实际墙钟会被显存换页、batch 调度钝化，倍数通常小于理论值）。
2. **Qwen3-VL-32B prefill**（一次性，但对本机是主导项）：
   - vision token：480p match **390 → 4128**（10.6×）；768p match **1008 → 4128**（4.1×）；
   - vision encoder patch 数：4128 token × 4 = **16512**（4K 档 29184）；
   - 编码器 int8 权重 ~27 GB，8 GB 卡必然分层卸载到 CPU/内存 ⇒ 这段的绝对时间远超采样。

## 3. 质量：`max` 改善的是什么

H3 的 2D RoPE 用 `_axis_from_sqrt_area`（`comfy/ldm/minimax/model.py` L70-92）：坐标网格按 `√(h·w)` 归一化，参考图与目标帧**各用自己的网格，但落在同一个归一化坐标空间**。

⇒ **参考内容在画面里占多大，只由宽高比决定，与分辨率无关**。分辨率只决定同一块构图被**采样多细**。因此：

- 想改善**构图 / 运镜 / 镜头一致性** → 换 `max` 无效，应改宽高比匹配、参考图内容与提示词；
- 想改善**身份 / 人脸 / 文字 / logo / 纹理保真** → `max` 有效，且是两条支路同时变细：

| 支路 | 480p `match` | 2752×1536 `max` | 倍数 |
|---|---|---|---|
| Qwen3-VL 输入面积 | 832×480 = 0.40 MP | 2752×1536 = 4.23 MP | 10.6× |
| Qwen3-VL vision token | 390 | 4128 | 10.6× |
| VAE / DiT 参考 rows | 390 | 4128 | 10.6× |

`match` 在 480p 下只给文本编码器 0.40 MP —— 人脸特征、招牌文字、服饰纹样这类细节**在编码阶段就被抹掉**，生成端再强也拿不回来。这是 `max` 的主要收益来源。

## 4. `max` 模式下的"密度旋钮"表（16:9 素材）

选定 `max` 后，参考密度**完全由你提供的素材分辨率决定**（只要短边 ≤ 2048）：

| 素材（16:9） | `max` 实际进入 | token | 占 2048 封顶 | 480p 注意力 | 768p 注意力 |
|---|---|---|---|---|---|
| 1920×1080 | 1920×**1088** | 2040 | 28% | 1.22× | 1.05× |
| 2048×1152 | 2048×1152 | 2304 | 32% | 1.26× | 1.07× |
| 2560×1440「2K」 | 2560×1440（不缩） | 3600 | 49% | 1.45× | 1.14× |
| **2752×1536** | **2752×1536（不缩）** | **4128** | **57%** | **1.54×** | **1.17×** |
| 3200×1792 | 3200×1792（不缩） | 5600 | 77% | 1.78× | 1.25× |
| **3648×2048** | **3648×2048（不缩）** | **7296** | **100%** | **2.08×** | **1.35×** |
| 3840×2160「4K」 | 压回 **3648×2048** | 7296 | 100%（与上行**完全等价**） | 2.08× | 1.35× |
| 7680×4320「8K」 | 压回 **3648×2048** | 7296 | 100%（同上） | 2.08× | 1.35× |

（1920×1080 → 1088 是 `round(1080/32)=34` 的对齐结果，+0.7%；其余各行都是 32 的整数倍，零损失。）

**读法**：这张表就是"选 `max` 时该用哪个分辨率"的直接答案——**要更好就把短边推到 2048（16:9 = 3648×2048）；再大没有收益，只有多余的读取与 lanczos 缩放时间。**

## 5. 质量 / 速度最优解

| 场景 | 推荐组合 | 理由 |
|---|---|---|
| **768p 生成（任何场景）** | `max` + 素材短边尽量 2048（3648×2048） | 序列只 +8%、注意力 1.17×（素材 2752×1536）到 1.35×（素材 3648×2048）——这是**性价比最高的组合**，保真提升几乎免费 |
| **768p，手头只有 2752×1536** | `max` + 2752×1536 | `max` 对它零缩放、零重采样，4128 token，成本 1.17×，没有理由不开 |
| **480p 常规 / 多图** | `match` + 2752×1536 | 多图时参考 token 是硬约束（§7），`match` 每张只加 390 token |
| **480p 关键 1–2 张**（人脸 / 文字 / logo 是主体） | 单独切 `max` + **2752×1536** | **4128 token / 1.54× 就是 480p 的性价比点**：密度已是 `match` 的 10.6×，成本远低于 4K 档 |
| **480p 追求封顶保真（单张）** | `max` + 3648×2048 | 密度吃满 7296（2.08×）；**前提是这 2048 短边的细节真实存在**，且需先验证 8 GB 显存与耗时 |

一句话：**768p 无脑 `max`；480p 用 `max` 但只用 2752×1536，别为了凑 2048 去放大。**

## 6. 与 Qwen-Image 2.1 链路的衔接

奇数但关键的一致性：**2752×1536 正是 Qwen-Image 2.1 官方 16:9 原生档**（官方 7 档 ≈4.2 MP，见 `refs/Qwen-Image-2.1/README.md` L138-151），而 H3 的 `max` 对它不缩放 ⇒ **Qwen 出图 → H3 参考，全程零重采样、零对齐损失**。

推论：

- **把 2752×1536 放大到 3648×2048 再喂 H3 是净亏**：H3 会按 7296 个采样点去"看"插值出来的平滑纹理，**逐像素不产生新信息**，身份/文字保真不会提升，反而多 35% 注意力成本与潜在插值伪影。
- **要真正吃到 2048 短边的收益，素材必须原生就有 2048 短边的细节**：4K 拍摄 / 渲染，或超分模型（SUPIR / SeedVR2）产生真实纹理，或让 Qwen 直接原生生成 3648×2048（**超出官方 2K 域，属外推，质量与结构重复风险未验证**）。
- 因此判据是：**决定质量上限的是素材的真实信息量，`max` 只是防止它被自动压扁。**

## 7. 多图预算与边界

- **预算经验（沿用口径文档 §7）：参考 token 总量别超过视频 token 的一半。**
  - 480p 5 s：视频 14430 ⇒ 预算 ≈ 7200 ⇒ 单张 2752×1536（4128）安全，再有第二张就吃紧；单张 3648×2048（7296）已到顶，两张必爆。
  - 768p 5 s：视频 37296 ⇒ 预算 ≈ 18600 ⇒ 两张 3648×2048（14592）仍有余量。
- **9 张 4K + max @480p ≈ 26× 注意力，8 GB 卡基本必 OOM**；同场景改 `match` 只多 3510 token（几乎无感）。
- **Qwen 侧独立限制**：`max_pixels = 12845056`（≈12.85 MP，`qwen_vl.py` L39-46）。2752×1536 = 4.23 MP、3648×2048 = 7.47 MP 都安全；只有当宽高比 > 3.06:1 时 Qwen 才会二次缩小，导致 Qwen 与 VAE 看到不一致的尺寸。
- **两档完全等价的边界**：素材面积 ≤ 生成画布面积（480p ≤ 0.40 MP、768p ≤ 1.03 MP）时 `match` = `max`（`scale` 都是 1.0）。

## 9. 复算脚本（纯标准库，可直接复跑）

```python
import math

ALIGN, SHORT = 32, 2048          # CANVAS_MULTIPLE, REF_IMAGE_SHORT_EDGE
align = lambda x: max(ALIGN, round(x / ALIGN) * ALIGN)

def node_size(w, h, mode, gw=0, gh=0):
    scale = (min(1.0, math.sqrt((gw * gh) / (w * h))) if mode == "match"
             else min(1.0, SHORT / min(w, h)))
    return align(w * scale), align(h * scale)

tok = lambda w, h: (w // 32) * (h // 32)   # 每 32×32 像素 = 1 token

LATENT_T, TEXT_AUDIO = 37, 800
DOC = {                                     # 生成档 -> (画布宽, 画布高) -> 视频 token
    "480p": (832, 480),
    "768p": (1344, 768),
}
video = {k: tok(*v) * LATENT_T for k, v in DOC.items()}

# 1) 2752x1536 的两档对比
W, H = 2752, 1536
for k, (gw, gh) in DOC.items():
    rw, rh = node_size(W, H, "match", gw, gh)
    mw, mh = node_size(W, H, "max")
    vm = video[k] + tok(rw, rh) + TEXT_AUDIO
    vx = video[k] + tok(mw, mh) + TEXT_AUDIO
    print(f"{k}: match->{rw}x{rh} tok={tok(rw,rh)} 序列={vm} | "
          f"max->{mw}x{mh} tok={tok(mw,mh)} 序列={vx} | "
          f"序列+{(vx/vm-1)*100:.1f}% 注意力{(vx/vm)**2:.2f}x")

# 2) 密度旋钮表：max 下不同素材的 token 与 480p/768p 成本
for w, h in [(1920,1080),(2048,1152),(2560,1440),(2752,1536),
             (3200,1792),(3648,2048),(3840,2160),(7680,4320)]:
    mw, mh = node_size(w, h, "max")
    row = f"{w}x{h} -> {mw}x{mh} tok={tok(mw,mh)} ({tok(mw,mh)/7296*100:.0f}% 封顶)"
    for k, (gw, gh) in DOC.items():
        rw, rh = node_size(w, h, "match", gw, gh)
        vm = video[k] + tok(rw, rh) + TEXT_AUDIO
        vx = video[k] + tok(mw, mh) + TEXT_AUDIO
        row += f"  {k}注意力{(vx/vm)**2:.2f}x"
    print(row)
```

```text

768p: match->1344x768 tok=1008 序列=39104 | max->2752x1536 tok=4128 序列=42224 | 序列+8.0% 注意力1.17x
```

## 10. 一句话交接

**2752×1536 在 `max` 下就是原样直通（4128 token，占 2048 封顶的 57%）：768p 开 `max` 几乎免费（1.17×）应无脑开；480p 把它留给关键那 1–2 张（1.54×）；要更好就得拿原生短边 2048 的素材（3648×2048，7296 token），而不是把 2752×1536 放大。**
