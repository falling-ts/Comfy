# Qwen-Image 2.1 与 MiniMax H3 的 Token 占比口径对照

> 日期：2026-10-07
> 问题：Qwen-Image 2.1 在各种尺寸下每个部分占多少 token；H3 参考图与生成图的 token 占比；占比多少才有效；是不是越高越好
> 依据：全部按源码复算，无随机性（公式见 §7）
> 相关：`docs/MiniMax-H3-人物身份遵循诊断-2026-10-07.md`（本工作流的具体诊断）、`docs/MiniMax-H3-参考图尺寸与match-max口径-2026-10-02.md`、`docs/MiniMax-H3-2752x1536参考图-max与match的成本收益-2026-10-02.md`

---

## 0. 结论摘要

1. **两个模型的 token 网格完全相同：每 32×32 像素 1 个 token**（VAE `//16` 下采样 + patchify `(1,2,2)`）。所以 **token 数 == 像素面积 / 1024**。
2. **Qwen-Image 2.1 的 `resolution` 是【面积】语义，不是短边语义**：`W×H ≈ resolution²`。`resolution=1024` ⇒ 任意比例都约 1030 token；`resolution=2048` ⇒ 约 4080 token。**H3 的 `max` 是【短边】语义**：短边压到 2048。
3. **「占比」必须拆成三个独立的量**，混在一起会互相抵消：
   - **A 画布占位**（归一化重叠 overlap）—— 决定**空间对齐**，**只看宽高比**
   - **B 参考端密度**（参考图 token 数）—— 决定**身份细节预算**，看像素面积
   - **C 生成端密度**（输出帧 token 数）—— 决定**能复现的最小结构**，看输出分辨率 × 景别
4. **不是占比越高越好。** 关键门是 **参考端头高 ≥ 输出端脸高**（密度不欠采样）。当前 1088×1920 立绘头高 342px ≥ 480p-MCU 的 158px ⇒ **这一项本来就通过**。
5. **你当前失败的其实是 A（画布占位），不是 B/C。** 画布重叠只有 **57%**，头映射后 y=−0.127 完全在画面外。**A 失败无法用任何参数补救，只能换参考图构图。**
6. **三个猜测的判定**：
   - 「参考占比低、生成占比高 ⇒ 一定有失真」—— **成立**，这是欠采样。
   - 「参考占比高、生成占比低 ⇒ 还会失真吗」—— **会掉分，但不会崩塌**。失真形态是「特征被抹成平均脸」（ArcFace 掉分），**不是「变成别人」**（身份错误）。方向相反：前者欠采样，后者超采样。
   - 「占比极高但实际生成画面占比低 ⇒ 效果不会降低」—— **只在 A 也成立时才对**。若画布重叠不足，占比再高也没用（主体已被裁掉）。
7. **参考图开到 2048×1152 即饱和**：max 下 2304 token；再上 2752×1536 只多 1.79× token，而注意力是 O(S²)，收益远小于此。**2048 短边封顶值 = 7281 token**（16:9），1088×1920 只占 28%。

## 1. Qwen-Image 2.1 的 token 口径

### 1.1 源码证据

`ComfyUI/comfy_extras/nodes_qwen.py` L181（`TextEncodeQwenImage21.execute`）：

```python
latent = torch.zeros([1, 64, latent_h // 16, latent_w // 16], ...)
```

`ComfyUI/comfy/ldm/qwen_image/model.py` L403-427（`process_img`）：

```python
hidden_states = hidden_states.reshape(bs, T * (h // 2) * (w // 2), C * 4)   # L410
h_len = ((h + (patch_size // 2)) // patch_size)                            # L412, patch_size=2
w_len = ((w + (patch_size // 2)) // patch_size)                            # L413
```

⇒ 64 通道 latent，`//16` 空间下采样，patchify 2×2 ⇒ **1 token = 32×32 像素**。

### 1.2 `resolution` 是面积语义（易误读点）

`nodes_qwen.py` L155-161：

```python
if resolution > 0:
    ratio = samples.shape[3] / samples.shape[2]
    width  = round(math.sqrt(resolution * resolution * ratio) / 32) * 32
    height = round(math.sqrt(resolution * resolution / ratio) / 32) * 32
else:
    width, height = round(W / 32) * 32, round(H / 32) * 32
```

`W×H ≈ resolution²`，所以 **token ≈ resolution² / 1024**，且与比例无关：

| `resolution` | 1:1 | 16:9 | 9:16 | 4:3 | token |
|---|---|---|---|---|---|
| 1024 | 1024×1024 | 1376×768 | 768×1376 | 1184×896 | **≈1030** |
| 1536 | 1536×1536 | 2048×1152 | 1152×2048 | 1760×1344 | **≈2300** |
| 2048 | 2048×2048 | 2720×1536 | 1536×2720 | 2368×1760 | **≈4080** |

⚠️ **`resolution` 与 H3 的 `max` 不是同一个口径**：1024 是「面积 1024²」，不是「短边 1024」。

## 2. H3 的三个「占比」量

### 2.1 A 画布占位（overlap）—— 只看宽高比

来自 `_axis_from_sqrt_area`（`comfy/ldm/minimax/model.py` L70-74）：

```
r_axis = dim / √(w·h)
span   = [ (1−r)/2 , (1+r)/2 ]
overlap = max(0, min(ref_y1, tgt_y1) − max(ref_y0, tgt_y0))
       × max(0, min(ref_x1, tgt_x1) − max(ref_x0, tgt_x0))
```

**含义**：参考图映射到目标帧后，有多大比例落在画面内。

- `overlap = 100%` ⇒ 主体按原比例落进目标帧，空间条件 1:1 迁移
- `overlap < 100%` ⇒ **被裁掉的恰好是构图的一部分**，且不知道是哪部分（要看轴向）

本工作流实测（目标 832×480，ratio 1.733）：

| 参考图 | 尺寸 | ratio | **overlap** |
|---|---|---|---|
| 场景图 ×2 | 832×480 | 1.733 | **100%** |
| 人物立绘 | 1088×1920 | 0.567 | **57%** |
| 2048×1152 | 2048×1152 | 1.778 | **99%** |
| 1536×864 | 1536×864 | 1.778 | **99%** |
| 2752×1536 | 2752×1536 | 1.792 | **98%** |
| ⚠️ 2048×2048 方图 | 2048×2048 | 1.000 | 76%（头贴 y=0.030） |

### 2.2 B 参考端密度

`max` 口径（`nodes_minimax_h3.py` L300-306，`REF_IMAGE_SHORT_EDGE=2048` L32）：

```
scale = min(1.0, 2048 / min(w, h))          # 只缩不放
tw = round(w*scale/32)*32 ; th = round(h*scale/32)*32
token = (tw/32) * (th/32)
```

16:9 下 **2048 短边封顶值 = 7281 token**（3648×2048）：

| 参考图 | scale | max 后 | **token** | 占封顶 |
|---|---|---|---|---|
| 1088×1920 | 1.0000 | 1088×1920 | 2040 | 28.0% |
| 1536×864 | 1.0000 | 1536×864 | 1296 | 17.8% |
| **2048×1152** | 1.0000 | 2048×1152 | **2304** | 31.6% |
| 2752×1536 | 1.0000 | 2752×1536 | 4128 | 56.7% |
| 3840×2160 | 0.8889 | 3648×2048 | 7296 | ~100% |
| 4096×2304 | 0.8889 | 3648×2048 | 7296 | ~100% |

⇒ **4K 与「短边 2048」在 max 下完全等价**，想吃满细节要准备短边 2048 的素材。

### 2.3 C 生成端密度

`token = (W/32) × (H/32)`，再乘景别得脸高 token：

| 档位 | 帧 token | 中景 25% | MCU 33% | 特写 50% |
|---|---|---|---|---|
| **480p** 832×480 | 390 | 120px / 3.8 | 158px / **5.0** | 240px / 7.5 |
| **768p** 1344×768 | 1008 | 192px / 6.0 | 253px / **7.9** | 384px / 12.0 |
| 1080p 1920×1088 | 2040 | 272px / 8.5 | 359px / 11.2 | 544px / 17.0 |

## 3. 核心判据：三道门

> **任意一道不满足都会掉分，但性质完全不同。**

| 门 | 判据 | 不满足的后果 | 可否用参数补救 |
|---|---|---|---|
| **门 1** | **画布 overlap ≥ 90%** | 主体被裁，**空间条件完全失效** | ❌ **不可**，必须换参考图构图 |
| **门 2** | **参考端头高 ≥ 输出端脸高** | 欠采样 ⇒ 骨相失真（放大插值） | ✅ 加大参考图 / 降低输出分辨率 |
| **门 3** | **参考端头 token ≥ 64** | 特征分辨率不足 ⇒ 抹成平均脸 | ✅ 同上 |

### 3.1 当前 0044 的三门体检

| 门 | 实测 | 判定 |
|---|---|---|
| 门 1 overlap | **57%** | ❌ **失败**（头映射后 y=−0.127，在画面外） |
| 门 2 头高 | 参考 342px vs 输出 158px（480p MCU） | ✅ 通过（342 ≥ 158） |
| 门 3 头 token | **67** | ⚠️ 勉强通过（≥64） |

> **这就是为什么「换更大的参考图」无效**：门 2、门 3 本来就过了，**卡住的是门 1，而门 1 只能靠换构图解决。**

### 3.2 门 2 的最小参考图尺寸表

参考图构图为「中近景」（头占参考图高 55%）时：

| 输出档 | 景别 | 脸高 | **参考图最小尺寸** | 参考头 token |
|---|---|---|---|---|
| 480p | 中景 | 120px | 224×128 | 8 |
| 480p | MCU | 158px | 288×160 | 14 |
| 480p | 特写 | 240px | 448×256 | 34 |
| 768p | 中景 | 192px | 352×192 | 20 |
| 768p | MCU | 253px | 448×256 | 34 |
| 768p | 特写 | 384px | 704×384 | 80 |

⚠️ 上表是**密度下限**（门 2），不含门 1 的宽高比要求。**实际必须取两者的最大值**：宽高比对齐 16:9 + 尺寸满足密度。

## 4. 直接回答「占比越高越好吗」

**不是。** 分三种情况：

### 4.1 超采样（参考端 > 生成端）—— 安全，白花算力

```
2048×1152 → 1344×768:  参考头 697 tok vs 生成头 7.9 tok = 88×
2752×1536 → 1344×768:  参考头 1249 tok vs 生成头 7.9 tok = 158×
```

**多余 token 被注意力池化掉，不产生错误**，只是让 prefill 和 O(S²) 注意力变贵。**不升反降的唯一情况**是 8 GB 卡上多图叠加导致 OOM。

### 4.2 欠采样（参考端 < 生成端）—— 真正的失真

```
1088×1920 立绘, 头高 342px
要在 832×480 里占到 MCU 33% => 需 158px 输出
参考端只有 342px... 但映射到目标帧后是 342 x (480/1920) = 85.5px
```

⚠️ 注意这里有两种「缩小」：
- **几何缩放**（宽高比不一致导致的轴向压缩）：85.5px，**这是真正的失真源**
- **密度降级**（注意力池化）：不产生错误

**欠采样的判据是「输出端要求的像素数 > 参考图实际提供的像素数」，不是 token 比值。**

### 4.3 门 1 失败时，占比再高也没用

当前情况：参考端头 67 token（门 3 勉强过），但 **overlap 57%，头根本不在画面里**。

> **「参考占比极高、生成占比低 ⇒ 效果不会降低」这个推断不成立** —— 它的前提是门 1 也通过。
> 只有在 overlap ≥ 90% 的前提下，「参考端超采样」才是安全的。

## 5. 你的三个猜测的逐条判定

| 猜测 | 判定 | 机制 |
|---|---|---|
| 「参考占比低，生成画面占比高，一定有失真」 | ✅ **成立** | 欠采样：输出端要求的像素数超出参考图供给，需插值/重绘 ⇒ 骨相失真 |
| 「参考占比高，生成占比低，还会有失真吗」 | ⚠️ **会掉分，但不会崩塌** | 超采样：多余 token 被池化。失真形态是**特征被抹成平均脸**（ArcFace 掉分），**不是变成别人**（身份错误）。方向与前者相反 |
| 「占比极高但生成画面占比低，效果不会降低」 | ❌ **不成立（无条件）** | 只在门 1（overlap ≥ 90%）通过时成立。当前 overlap 57%，占比再高都被裁掉 |

**一句话**：**欠采样伤骨相（变成别人），超采样只是浪费，门 1 失败则一切归零。**

## 7. 复跑公式

```
# token 网格（Qwen-Image 2.1 与 H3 相同）
token = (W/32) * (H/32) = 像素面积 / 1024

# Qwen-Image 2.1 的 resolution（面积语义）
ratio = W/H
W = round(sqrt(res^2 * ratio)/32)*32 ; H = round(sqrt(res^2/ratio)/32)*32

# H3 的 max（短边语义）
scale = min(1, 2048/min(w,h))
token = (round(w*scale/32) * round(h*scale/32))

# A 画布占位
r = dim / sqrt(w*h) ; span = [(1-r)/2, (1+r)/2]
overlap = ovl(span_ref_y, span_tgt_y) * ovl(span_ref_x, span_tgt_x)

# C 生成端脸高 -> token
face_px = frame_height * 景别占比      # 中景 .25 / MCU .33 / 特写 .50
face_tok = face_px / 32

# 门 2：参考端头高 vs 输出端脸高
ref_head_px = ref_height * (头占参考图高比例)
ok = ref_head_px >= frame_height * 景别占比
```
