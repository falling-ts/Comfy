## 一、官方基础事实(权威)

来源:`h3/MiniMax-H3/README.zh-CN.md`

| 项 | 事实 |
|---|---|
| 官方 checkpoint | **只有两个**:`H3-Base-FL2VA`(t2va / fl2va / i2v / l2v)、`H3-Base-Ref2VA`(ref2va) |
| 精度 | 均为 **BF16**,且是**经 CFG 蒸馏**的 Omni Transformer 权重 |
| 主干 | **33B 稠密单流 Transformer**,其中约 **13B 在 AdaLN 分支**;AdaLN 调制输出可预计算缓存 → **纯推理部署无需加载** → 这是所有 "pruned" 变体的来源 |

| 参考上限 | 图 ≤9、视频 ≤3(每段 2–15s,总 ≤15s)、音频 ≤3(须伴随图/视频)、混合总数 ≤12 |
| 文本编码器 | Qwen3-VL-32B 完整预训练权重,取**第 50 层隐藏态** |
| VisualVAE | f16t4d24(空间 16×/时间 4×/24 通道),再按 1×2×2 patchify → 进 Transformer 时**32× 空间下采样、4× 时间** |
| AudioVAE | 每声道 32kHz → **40Hz latent token** |
| 稀疏注意力 | 训练最后阶段引入,**初始开源版仅提供全注意力推理**,稀疏实现"后续更新单独发布" |
| 未开源组件 | **H3-Context-IR**(多模态指令预处理,官方称"对最终质量至关重要")、**H3-Regenerate-2K**(in-context 2K 重生成);二者仅 API 可用 |

> 官方推荐部署框架:SGLang(4 卡 + ulysses-degree 4)、vLLM、diffusers、ComfyUI。

## 六、加速方案全景(含项目内实测数据)

### 6.1 实测战报(`h3/minimax-h3-guide`,RTX 4070 Ti 12GB,20 步 R2V 双图参考 5s)

| 阶段 | 耗时 | 累计加速 |
|---|---|---|
| 原始(cu129) | ~480 s | 1× |
| + SageAttention + TE-Speed | ~261 s | 1.8× |
| **+ PyTorch cu130** | **47–74 s** | **6–8×** |

> **最大收益来自 torch cu130**:激活 comfy-kitchen 的 CUDA 硬件 kernel(INT8 convrot 硬件反量化 + NVFP4 硬件路径),把 DiT 量化开销从软件模拟变为硬件直算。**本机已是 torch 2.13.0+cu130,该项收益已吃到。**

### 6.5 🔑 核心内置稀疏注意力(0.35.0 新增,本机已验证可用)

**`comfy_extras/nodes_sparse_attention.py`(22.5 KB)注册 `BlockSparseAttention` 节点**(显示名 "Model Sparse Attention"),`method` 为一个 DynamicCombo,含三种方法:

| 方法 | 机制 | 权重要求 |
|---|---|---|
| **`sol-attn`**(默认) | Sparsifying Online Attention,**训练无关**自适应阈值,参数 `tau` 默认 1.3(tau=1.0 保留约 16% key blocks,1.5 约 7%,2.0 约 2.7%) | 任意权重 |
| `sla` | 固定百分比 top-k | **仅可用于专门蒸馏过的权重** |
| `vsa` | Video Sparse Attention,用模型 `to_gate_compress` 层 | **需 FastH3-VSA 权重** |

节点其余输入:`start_percent` 默认 **0.2**(此前保持稠密)、`end_percent` 默认 1.0、`dense_blocks`(如 `"0, 1, 47-49"` 恒稠密)、`min_tokens` 默认 **12288**(短于此保持稠密)、`extra_tokens` 默认 **256**(VSA 忽略)、**`sink_conditioning`(H3 专用)**:`exact_kv`(每个 query 精确attend 打包的 text/audio/reference 行,约 3% 开销)/ `exact_kv_and_rows`(另让目标音频 query 行稠密)、`verbose`。

**关键事实**:
- **H3 主干本身就是 VSA-trained 的**:`comfy/ldm/minimax/model.py` 注释 "VSA gate, unused by the dense forward; consumed by sparse attention patches";`model_detection.py` 按 state_dict 是否含 `to_gate_compress.weight` 判定 → `vsa` 可用性**取决于具体检查点**。
- **本机实测**:`minimax_h3_fl2va/ref2va_pruned_int8_convrot.safetensors` 各 **932 个键,均不含 `gate_compress`** → **本机权重只能走 `sol-attn`(训练无关)**,`vsa`(需 FastH3-VSA 权重)与 `sla`(需专门蒸馏权重)在本机权重上不可用。
- 本机依赖侧已满足:`comfy_kitchen` 导出 `sol_attn` / `sol_attn_chunked` / `sol_attn_is_available`,要求 **sm_80+(cp.async + INT8 MMA)**;本机 `torch.cuda.get_device_capability()` = **(8, 9) → 适用,`sol_attn_is_available()` 返回 True**。
- **KJNodes 的 H3 Sage 补丁与稀疏注意力的组合顺序必须是:`KJ Sage → H3 Mem-Eff Sage → Sol`**;且 H3 专用 Sol 节点会**绕过 `optimized_attention_override` 钩子**。
- SageAttention3 **仅 Blackwell 支持**(本机 `sageattn` 无 `sageattn3`),本机走 SageAttention 2.2.0 的 sm89 路径。

### 8.2 关键实测基线

**(a) 同型号硬基准(RTX 4060 8GB / 8188 MiB + 32GB RAM)** —— 最贴近本机

### 8.5 两段式真实参数与三个源码级坑

**本地模板实测**(逐一导出节点):`MiniMaxH3ReferenceToVideo` 1344×768/124 帧 → 第一段 **`res_multistep` + `BasicScheduler(simple, 25, 1)`** → `MiniMaxH3LatentUpscale(scale_by=2, bilinear)` + `MiniMaxH3ConditioningUpscale(scale_by=2)` → 第二段 **`ManualSigmas` 11 点(即 10 步)** → 音频分支 `MiniMaxH3ShiftSigmas(12.0, 3.0)`。
> 流传的「1.615 / 8 步 / denoise 0.4」**不匹配本地模板**;rockerBOO README 明说 `1.5 / 15 步 / 0.4` 只是**起始点**。本地插件提交 `a5ed6e9` 已把第二段换成 `ManualSigmas`。

1. **必须用 `MiniMaxH3AddNoise` 替代原生 `AddNoise`** —— H3 是 `CONST` 参数化,`SamplerCustomAdvanced + DisableNoise` 内部会**再调一次** `noise_scaling`;实测 denoise=0.4 时直接解码原生 `AddNoise` 输出**就是纯噪声**。
2. **音频必须用 `MiniMaxH3ShiftSigmas`**(12.0→3.0) —— denoise=0.4(σ_v=0.4)时模型期望 σ_a≈**0.14**,用视频 sigma 给音频加噪会致**音频失真**。
3. **缩放对齐** —— latent 放大向上取整到 2 的倍数(DiT patch `(1,2,2)`,奇数会崩);`ConditioningUpscale` **必须同参**,否则 reference/keyframe token 尺度与 RoPE 行布局错位。

> **kijai 立场**:"latent upscaling is always bad unless trained" → 推荐 **decode → 像素域放大(lanczos / RTX / SeedVR2)→ re-encode → 低 denoise 重采样,并复用第一段音频**。这与**有训练的** 3D 卷积 latent 放大器([LBH-123-AI](https://huggingface.co/LBH-123-AI/Minimax_h3_latent_Upscaler),80k 配对样本)不矛盾,后者宣称避免朴素插值重影,且**省时间不省 VRAM**。
>
> **8GB 判断**:两段式第二段在**目标全分辨率**跑采样,而 1344×768 已是你硬基准的帧数上限 → **8GB 上仅短片段可行**。

### 9.4 🔑 对 3010 旋镜视频的直接约束(与提示词相关)

| 项 | 数值 |
|---|---|
| H3 官方**安全环绕速率** | **≈ 24°/s**(上限被 clamp 40°/s) |
| 完整 360° 所需 | **≥ 9 秒 / ≥ 220 帧** |
| 本机 3010 现状 | 10 秒 → `align_frame_count` 对齐到 **243 帧(10.125 s)**;扣掉"迅速前飞"后**旋转仅约 8.6 s ≈ 42°/s,超安全速率** |
| 建议 | 视频秒数改 **12 秒**(→294 帧,旋转约 10.25 s ≈ 35°/s)或 **15 秒**(→362 帧,旋转约 13 s ≈ 27.7°/s,最接近安全值) |

> 结论:"迅速前飞 + 完整 360° 旋转"在 H3 里存在张力 —— 前飞占用的时间会挤压旋转时长。若要**既快又稳**,建议前飞压缩到 1–1.5 秒并把总时长提到 12–15 秒;若坚持 10 秒,旋转速率将超出官方安全区间,易出现翻滚/倾斜。
